Veille technologique

🔐 Sujet : Sécurité des applications web

Ma veille technologique porte sur la sécurisation des applications web, notamment comment protéger les données des utilisateurs et éviter les failles les plus courantes recensées par l'OWASP (Open Web Application Security Project).

Pourquoi ce sujet ?

J'ai choisi ce sujet car après mon BTS SIO, je souhaite poursuivre mes études dans le domaine de la cybersécurité. En développant mes projets PHP (RMS Ticket, Le Muscle Sympa), je me suis rendu compte que les failles les plus courantes (injections SQL, XSS, mots de passe mal stockés) s'appliquaient directement à mon code. Cette veille m'a permis de comprendre ces risques et d'y répondre concrètement.

Questions que je me suis posées :

  • Comment empêcher un utilisateur malveillant de manipuler mes requêtes SQL ?
  • Comment bien stocker les mots de passe en base de données ?
  • Comment éviter qu'un script JavaScript malveillant s'exécute sur mon site ?

📊 Comment j'ai effectué ma veille

  • OWASP.org : Site de référence mondial sur la sécurité web, avec des fiches pratiques claires
  • PHP.net : Documentation officielle PHP, consultée pour vérifier l'utilisation correcte des fonctions de sécurité
  • Google Alerts : Alertes sur "injection SQL PHP" et "sécurité PHP" pour suivre les actualités

📝 Ce que j'ai appris

Faille n°1 — L'injection SQL

📅 Janvier 2026 • Source : OWASP Cheat Sheet & PHP.net

C'est quoi ? Un attaquant tape du code SQL directement dans un champ de formulaire pour manipuler la base de données. Par exemple, taper ' OR '1'='1 dans un champ de connexion peut donner accès à tous les comptes.

Comment j'évite ça ? En utilisant les requêtes préparées (PDO) en PHP. Au lieu de coller directement la variable dans la requête :

// ❌ Dangereux
$sql = "SELECT * FROM users WHERE email = '" . $_POST['email'] . "'";

// ✅ Sécurisé avec PDO
$stmt = $pdo->prepare("SELECT * FROM users WHERE email = :email");
$stmt->execute([':email' => $_POST['email']]);

💡 Pourquoi ça marche ? PDO sépare le code SQL des données : la valeur saisie est traitée comme une simple chaîne de caractères, jamais comme du code.

🔗 Appliqué dans : RMS Ticket — toutes mes requêtes utilisent PDO avec des paramètres liés. Le Muscle Sympa — les formulaires de contact et d'inscription utilisent également PDO pour interroger la base de données.

Faille n°2 — Le XSS (Cross-Site Scripting)

📅 Février 2026 • Source : OWASP

C'est quoi ? Si un utilisateur saisit <script>alert('piraté')</script> dans un formulaire (ex : commentaire, nom…) et que je l'affiche sans protection, ce script s'exécute dans le navigateur de tous les visiteurs.

Comment j'évite ça ? Avec la fonction PHP htmlspecialchars() qui transforme les balises HTML en texte inoffensif avant l'affichage :

// ❌ Dangereux : affiche le script tel quel
echo $_GET['nom'];

// ✅ Sécurisé : <script> devient du texte affiché, pas exécuté
echo htmlspecialchars($_GET['nom'], ENT_QUOTES, 'UTF-8');

💡 Résultat : Le <script> malveillant apparaît comme du texte à l'écran au lieu de s'exécuter.

🔗 Appliqué dans : RMS Ticket — tous les affichages de données provenant de la base de données passent par htmlspecialchars(). Le Muscle Sympa — les noms et messages saisis dans les formulaires sont échappés avant affichage.

Faille n°3 — Stockage des mots de passe

📅 Février 2026 • Source : OWASP Cheat Sheet

C'est quoi le problème ? Si la base de données est compromise et que les mots de passe sont stockés en clair (ou en MD5), l'attaquant les a immédiatement. Il faut les hacher, c'est-à-dire les transformer en une empreinte impossible à retrouver.

Comment je le fais ? Avec les fonctions natives PHP password_hash() et password_verify() :

// ❌ Dangereux : mot de passe en clair ou MD5
$mdp = $_POST['password'];  // stocké tel quel

// ✅ Sécurisé : hachage avec bcrypt
$hash = password_hash($_POST['password'], PASSWORD_BCRYPT);
// Stocke $hash en BDD (ex: $2y$10$abc123...)

// Lors de la connexion :
if (password_verify($_POST['password'], $hash)) {
    // Connexion autorisée
}

💡 Pourquoi pas MD5 ? MD5 est trop rapide et il existe des tables de correspondance (rainbow tables) qui permettent de retrouver le mot de passe original. password_hash() utilise bcrypt qui est volontairement lent et ajoute un "sel" aléatoire automatiquement.

🔗 Appliqué dans : RMS Ticket — les mots de passe sont hachés avec PASSWORD_BCRYPT à l'inscription. Le Muscle Sympa — même fonctionnement pour les comptes utilisateurs du site.

🛠️ Application dans mes Projets

RMS Ticket

Améliorations de sécurité appliquées :

  • ✅ Requêtes préparées PDO (prévention injection SQL)
  • ✅ Hachage bcrypt pour les mots de passe
  • ✅ Échappement HTML avec htmlspecialchars()
  • ✅ Sessions sécurisées (httpOnly, SameSite)
  • ✅ Contrôle d'accès par rôles (admin/user)

Le Muscle Sympa

Bonnes pratiques implémentées :

  • ✅ Requêtes préparées PDO
  • ✅ Hachage bcrypt pour les mots de passe
  • ✅ Validation côté serveur des formulaires
  • ✅ Filtrage avec filter_var() (emails, URLs)
  • ✅ Échappement des données affichées

📌 Ce que j'ai retenu

Ces trois points m'ont appris que la sécurité web ne nécessite pas forcément des outils complexes : PHP fournit des fonctions natives (PDO, htmlspecialchars(), password_hash()) qui, si on les utilise systématiquement, protègent contre la majorité des attaques courantes.

Le point commun de ces trois failles : elles viennent toutes de données saisies par l'utilisateur que l'on fait confiance à tort. La règle d'or est donc : ne jamais faire confiance à une entrée utilisateur.
